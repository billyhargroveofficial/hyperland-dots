# Запись экрана — wf-recorder + NVENC

Кнопка в waybar (`image#recorder` с Lucide SVG), скрипт
`.config/waybar/scripts/recorder.sh`.
Клик — старт, повторный клик — стоп, файл в `~/records/*.mp4`.

## Флага `-s` у wf-recorder нет

Ни в одной версии. Разрешение задаётся ffmpeg-фильтром:

```
-F "scale=1280:720"
```

С `-s 1280x720` процесс умирает сразу после старта. Снаружи это выглядит
особенно обидно: уведомление «Запись начата» показывалось, кнопка ничего не
записывала, а повторный клик не останавливал — потому что останавливать было
нечего. Список реальных флагов: `man wf-recorder` или
[manpage в репозитории](https://github.com/ammen99/wf-recorder/blob/master/manpage/wf-recorder.1).

## `-x yuv420p` обязателен для NVENC

`wlr-screencopy` отдаёт кадры в XRGB8888, NVENC такое не принимает и падает на
первом кадре. Заодно `yuv420p` — единственный формат, который открывают все
плееры и браузеры.

## `-r 60` обязателен на этом мониторе

DP-3 работает на **200 Гц**, а без `-r` wf-recorder берёт частоту источника.
Получится файл на 200 fps: втрое больше по размеру, и ни один сценарий этих
кадров не просит.

## NVENC не кодирует маленькие кадры

При записи узкой области (например, полосы панели 300×38 для разбора анимации)
NVENC отваливается:

```
InitializeEncoder failed: invalid param (8): Frame Dimension less than the minimum supported value.
```

Для служебных записей маленьких областей брать `-c libx264`. Для обычной
записи экрана — `-c h264_nvenc`.

## Запись выходила светлее экрана

Симптом: видео заметно светлее и «площе», чем то, что было на мониторе.

Причина — рассогласование диапазона яркости. `wlr-screencopy` отдаёт кадры
полным диапазоном (RGB 0–255), кодировщик сжимал их в телевизионный 16–235,
но помечал файл как **полный** (`pix_fmt=yuvj420p`, `color_range=pc`). Плеер
такую метку уважает и обратно не растягивает — чёрный получается 16 вместо 0.

Проверяется объективно: снять `grim` и кадр из записи, взять одну и ту же
область и сравнить средний цвет.

```bash
ffmpeg -v error -i кадр.png -vf scale=1:1 -f rawvideo -pix_fmt rgb24 - | od -An -tu1
```

Замер до починки давал **+11/+12/+12** к каналам. Формула сходится точно:
36 × 219/255 + 16 = 47.

Лечится заданием всей цепочки явно — половинчатые варианты промахиваются в
другую сторону (проверено: только `out_range=full` дало −4/−8/−9, только
`-p color_range=tv` дало −10/−7/−5, потому что преобразование применялось
дважды):

```
-F "scale=1280:720:in_range=full:out_range=limited:out_color_matrix=bt709"
-p color_range=tv -p colorspace=bt709 -p color_primaries=bt709 -p color_trc=bt709
```

- `in_range=full` — сообщаем фильтру правду про вход, чтобы он не додумывал;
- `out_range=limited` + `color_range=tv` — сжимаем один раз и честно помечаем;
- `bt709` во всех трёх полях — иначе `color_space` остаётся `unknown` и плееры
  начинают гадать сами.

После этого замер той же области: расхождение **0/0/1**, метаданные
`yuv420p / tv / bt709`.

## Останавливать по PID, а не `pkill`

В скрипте PID пишется в файл, а перед остановкой сверяется
`/proc/<pid>/comm`. Причины:

- `pkill -INT wf-recorder` убьёт и чужую запись, если она идёт;
- голый `pidof` не отличает «идёт запись» от «процесс умер на старте», и
  каждый клик уходил бы в ветку старта.

После `SIGINT` надо **дождаться выхода процесса**: wf-recorder дописывает
moov-atom, без него mp4 не открывается ничем. Уведомление «сохранено» показывать
только после фактического завершения, а не сразу.

## Проверка, что запись живая

Скрипт ждёт 0.7 с после старта и проверяет, что процесс жив: почти все ошибки
(нет кодека, занят GPU, кривой фильтр) вылезают в первые полсекунды. Если
процесс умер — приходит уведомление с хвостом лога вместо ложного «Запись
начата». Лог: `$XDG_RUNTIME_DIR/wf-recorder.log`.

Безобидное предупреждение, которое всегда есть в логе и ничего не значит:

```
Changing video frame properties on the fly is not supported by all filters.
```

## Звук

Записи идут без звука намеренно. Включить — добавить `-a` в массив `args`
(дефолтный источник) или `-a <имя>` из `pactl list short sources`.
